## CONTEXT

Every inbound SMS already creates a row in the `messages` table and appears in the
unified inbox. Inbound phone calls do not. Call data lands in `call_events` but is
never written to `messages` — so staff looking at a customer's conversation thread
see SMS history but have no visibility into whether that customer called, was missed,
left a voicemail, or spoke to someone.

**Goal:** Every inbound call creates a `messages` row in the correct conversation thread,
the same way SMS does. The message row records direction, outcome, duration, and
recording URL (if voicemail). No UI work in this stage — just the persistence layer.

**Clean Machine is live.** Calls are being received today. The fix must not affect
existing call routing, TwiML responses, or IVR behavior in any way. It only adds
a write to the messages table as a side effect.

## THE FIX — TWO WRITE POINTS

### Write Point 1 — Call arrival (routes.twilioVoiceCanonical.ts)

When an inbound call arrives, write a `messages` row immediately — before any TwiML
is returned. This records that the call happened even if it is never answered.

The row should represent: "a call came in from this customer at this time."

**Steps:**
1. Resolve (or create) the conversation thread using `customerThreadService` with the
   caller's `From` phone number and the tenant's `To` number.
2. Insert into `messages`:
   - `conversationId` from the resolved thread
   - `tenantId` from the resolved tenant
   - `sender`: `'customer'` (inbound call — caller is the customer)
   - `body`: `'📞 Inbound call'` (placeholder — will be updated at call end if needed)
   - `messageType`: `'call_inbound'`
   - `metadata`: `{ callSid: CallSid, from: From, to: To, status: 'ringing' }`
   - `createdAt`: now
3. Store the new message row's `id` — you will need it to update status at call end.
   **The best place to store this is in the metadata of a `call_events` row**, if that
   table is being written at call arrival. Alternatively, it can be looked up later
   by `callSid` if metadata is indexed. Confirm the approach from your schema read.
4. Call `broadcastNewMessage` with the new row so the inbox updates in real time.
5. **Do not change the TwiML response.** The existing routing logic runs unchanged after
   this write. This is a pure side-effect.

**Error handling:** Wrap the entire write block in try/catch. If the thread resolution
or message insert fails, log the error and continue — the call must still be answered
even if persistence fails.

### Write Point 2 — Voicemail / recording complete

When a voicemail recording completes (the recording-status or voicemail-complete webhook
fires), update or insert a message row to reflect the voicemail outcome.

**Steps:**
1. Look up the existing `messages` row for this call using `callSid` (from the webhook's
   `CallSid` param). If found: update `messageType` to `'voicemail'`, update `metadata`
   to include `{ recordingUrl, recordingDuration }`, update `body` to `'📞 Voicemail left'`.
2. If no existing row found (defensive): create a new row with type `'voicemail'`,
   resolve thread from `To`/`From` if available in the webhook payload.
3. Call `broadcastNewMessage` with the updated row.

**Error handling:** Same as Write Point 1 — try/catch, log, never crash the webhook
response. Twilio must always receive a 200 from this webhook or it will retry.

## MISSED CALL HANDLING

A missed call is one where:
- Write Point 1 fired (call arrived) AND
- No answered/completed status was recorded AND
- The call ended (status callback receives `no-answer` or `busy` or `failed`)

Check whether there is already a Twilio status callback handler for voice calls:

```bash

  server/ --include="*.ts" | grep -v "node_modules" | head -20
```

If a status callback handler exists:
- Add logic to update the `messages` row to `messageType: 'call_missed'` and
  `body: '📞 Missed call'` when `CallStatus` is `no-answer`, `busy`, or `failed`.

If no status callback handler exists:
- Do not create one in this task. Flag it in the completion report under `DEFERRED ITEMS`.
  The call row will stay as `'call_inbound'` — not ideal but not broken. Missed call
  detection becomes Comms Hub Stage 1B.
