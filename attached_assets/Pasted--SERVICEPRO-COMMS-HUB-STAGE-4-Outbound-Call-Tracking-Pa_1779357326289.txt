## CONTEXT

Inbound calls now appear in the conversation thread (Stages 1–3). Outbound calls are
invisible. When staff call a customer back from Groundwire, nothing appears in their
thread. This stage tracks outbound calls as `messageType='call_outbound'` rows —
completing the two-way call picture in the unified inbox.

**How outbound calls work today:** The owner/staff uses Groundwire (a SIP softphone)
registered against the Twilio SIP domain. Twilio sees every outbound call placed from
that SIP client. The question is whether Twilio fires a status callback we can intercept,
or whether we need to configure one.

**Clean Machine is live.** Outbound calls are being placed today. The fix must not
affect call routing, audio quality, or Groundwire registration in any way.

## THE FIX — APPROACH DEPENDS ON VERIFICATION FINDINGS

### Path A — If outbound calls are placed via `client.calls.create`

Add a `statusCallback` URL to every outbound call initiation:

```typescript
await twilioClient.calls.create({
  to: customerPhone,
  from: tenantPhoneNumber,
  url: `${BASE_URL}/twilio/voice/outbound-initiated`,   // TwiML for the call
  statusCallback: `${BASE_URL}/twilio/voice/outbound-status`,
  statusCallbackMethod: 'POST',
  statusCallbackEvent: ['initiated', 'ringing', 'answered', 'completed'],
  // ... existing params unchanged
});
```

Then create the status callback handler (see Handler section below).

### Path B — If outbound calls are placed exclusively via Groundwire SIP

Twilio still fires status callbacks for SIP-originated outbound calls IF a status
callback URL is configured on the phone number or SIP trunk in the Twilio console.
The fix has two parts:

**Part 1 — Twilio console configuration (manual, one-time):**
- Twilio Console → Phone Numbers → your number → Voice Configuration
- Under "Call Status Changes" (or the SIP Domain settings): set the status callback
  URL to `https://YOUR-APP-URL/twilio/voice/outbound-status`
- Method: POST
- Report this URL in the completion report so it can be confirmed

**Part 2 — Backend handler** (same as Path A, see below).

### Path C — If a voice status callback handler already exists

Extend it to detect outbound direction and write the message row.
Do not create a duplicate handler.

## THE HANDLER — `POST /twilio/voice/outbound-status`

Regardless of path, this handler:

1. Receives Twilio's standard status callback payload:
   - `CallSid`, `CallStatus`, `Direction`, `From`, `To`, `Duration`, `DialCallDuration`
2. Only processes rows where `Direction = 'outbound-api'` or `'outbound-dial'`
   (ignore inbound — those are handled by existing routes)
3. Only fires on terminal status: `CallStatus === 'completed'`, `'no-answer'`,
   `'busy'`, or `'failed'`
4. Resolves the tenant from the `From` number (the Twilio number) using
   `getTenantByPhoneNumber()` — same pattern as inbound
5. Resolves the conversation thread from the `To` number (the customer) using
   `customerThreadService` — same pattern as `persistCallArrival`
6. Writes a `messages` row:
   - `messageType: 'call_outbound'`
   - `sender: 'staff'` (staff initiated the outbound call)
   - `body: 'call_status === completed ? '📞 Outbound call' : '📞 Outbound call — ' + CallStatus`
   - `metadata: { callSid: CallSid, direction: 'outbound', duration: Duration, status: CallStatus }`
7. Calls `broadcastNewMessage` with the new row
8. Entire handler wrapped in try/catch — always returns 200 to Twilio regardless
9. Add the route to the existing Twilio voice router — do not create a new router file

**Add `persistOutboundCall` to `callMessagePersistence.ts`** following the exact same
fail-open pattern as `persistCallArrival`, `persistVoicemailComplete`,
`persistMissedCall`.
