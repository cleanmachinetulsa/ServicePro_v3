## CONTEXT

Comms Hub Stage 1 (complete) wires every inbound call into the `messages` table with
`message_type` values of `'call_inbound'` | `'call_missed'` | `'voicemail'`. Those rows
already flow through the existing Socket.IO `broadcastNewMessage` channel.

Right now, `MessageBubble.tsx` (or equivalent) doesn't know what to do with a non-SMS
message type — it will either crash, render blank, or show raw text. This stage makes
call rows render as distinct, readable call cards in the NightOps inbox thread view.

**Goal:** Staff open a customer thread and see the full communication history — SMS
bubbles AND call events — in one chronological timeline. No new data fetching needed;
the rows are already there.

**Clean Machine is live.** SMS rendering must be byte-identical after this change.
Call cards are additive — they only render for rows where `messageType` is a call type.

## THE FIX — THREE TARGETED CHANGES

### Change 1 — Add `messageType` to the frontend Message type (if missing)

Find the `Message` interface or type used by the frontend. Add `messageType` as an
optional field with a default of `'sms'`:

```typescript
messageType?: 'sms' | 'call_inbound' | 'call_missed' | 'voicemail';
```

This is additive. Existing SMS message objects that don't include this field will
behave identically — the component will treat `undefined` as `'sms'`.

### Change 2 — Call card variant in MessageBubble

In `MessageBubble.tsx`, add a branch at the top of the render:

```typescript
const isCallEvent = message.messageType === 'call_inbound'
  || message.messageType === 'call_missed'
  || message.messageType === 'voicemail';

if (isCallEvent) {
  return <CallCard message={message} />;
}
// existing SMS render logic unchanged below
```

**`CallCard` component** — define it in the same file or as a sibling file
`client/src/components/messages/CallCard.tsx`:

The card should show:
- **Icon:** Phone icon for calls, Voicemail icon for voicemail (use lucide-react —
  `Phone`, `PhoneMissed`, `Voicemail` — confirm which are available)
- **Label:**
  - `call_inbound` → "Inbound call"
  - `call_missed` → "Missed call"
  - `voicemail` → "Voicemail"
- **Timestamp:** formatted time (same format as SMS bubbles — match exactly)
- **Duration:** if available in `message.metadata.recordingDuration` — show as "0:42"
  formatted. If not present, omit.
- **Recording playback:** if `message.metadata.recordingUrl` is present, show a
  simple inline audio player (`<audio controls src={recordingUrl} />`). Style it
  to fit the card width. Only show for `messageType === 'voicemail'`.
- **Visual style:** distinct from SMS bubbles — use a neutral card style
  (not the customer blue / AI gray bubble colors). A light gray background with a
  left border accent works well. Match the existing design system — use CSS variables
  and existing Tailwind tokens, not raw hex values.

**Do not** add click-to-call, do not add "Call back" buttons — that is a future stage.
**Do not** change anything in the existing SMS bubble render path.

### Change 3 — Thread list preview fallback

In `NightOpsConversationList.tsx` (or wherever the last-message preview text is
rendered), add a fallback for call message types so the preview doesn't show raw
"📞 Inbound call" body text but instead shows a clean label:

```typescript
const getMessagePreview = (message: Message): string => {
  switch (message.messageType) {
    case 'call_inbound': return '📞 Inbound call';
    case 'call_missed':  return '📞 Missed call';
    case 'voicemail':    return '📞 Voicemail';
    default:             return message.body ?? '';
  }
};
```

If the preview is already computed this way, or the body already contains the right
text from Stage 1, confirm it and skip this change. Do not add it twice.

|---|---|

| `metadata` is null or missing `recordingUrl` | Audio player omitted silently |
